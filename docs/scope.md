# Scope — paper-lineage

このドキュメントは「何を作るか / 作らないか」を固定するアンカー。

> **2026-07-29 スコープ改訂**: 当初は seed 論文1本の ego-network(上流2ホップ・下流2ホップ、間引き前提)を想定していたが、**分野まるごとを一度に描く**方向に切り替えた。理由は下記「なぜ全部描くのか」。旧版の「間引きをデフォルトにする」方針は破棄。

## 中心アイデア

論文の引用関係は **時間について厳密に単方向**(先行論文が後発論文を引用することは原則ない)。この制約は他のネットワーク(SNS、Web リンク、共著)にはない。既存の literature mapping ツールは force-directed レイアウトを主表現にしており、時間を色やフィルタとしてしか使っていない。

→ **時間軸を固定した単調レイアウトに、分野の引用グラフを全部流し込む。** そのとき現れる「互いに引用し合う太いライン」こそが見たいもの。

## なぜ全部描くのか

既存ツール(Connected Papers / Litmaps / Research Rabbit)の不満点:

1. **表示数が少なすぎる。** 数十件では、そこに映っているものが意味のある流れなのか、たまたま拾われた数本なのか判断できない。
2. **配置がネットワーク的で、時代の流れが読めない。** force-directed は時間方向を潰す。
3. 結果として「一本一本を精読する」ためのツールになっており、**全体のトレンド感**を掴む用途に向いていない。

paper-lineage が対象にするのは **個々の論文ではなく流れ**。だから:

- ノード数が数万〜十万でも構わない。**間引きは主要な設計手段にしない**(打ち切るとしても、それは性能上の妥協であって思想ではない)。
- 1ノードが1pxでも構わない。読ませたいのは点ではなく**帯**。
- ズームして初めて個別の論文が読める、というインタラクションでよい。

## 機能スコープ

### F1. 時間単調レイアウト(必須・主貢献)

- 時間軸を**固定**(年 = 一方の軸)。ここは絶対に動かさない。
- もう一方の軸(cross axis)の決め方が本質的な設計問題 → `algorithms.md` 参照。
  意味のない軸に置くと、ただの散布図になって流れが見えない。**同じ流れが同じ帯に留まり続ける**ように配置する必要がある。
- 数万〜十万ノードを 60fps で描く前提。SVG / DOM ベースでは足りない → **WebGL(deck.gl / regl / sigma.js)**。
- レイアウトは**決定的**であること。読み込むたびに絵が変わると「流れ」として記憶できない。

### F2. 太いラインの抽出(必須・このツールの答えたい問い)

全部描いたときに浮かび上がる「互いに引用し合う一本の流れ」を、**目視だけでなくアルゴリズムでも取り出して強調する**。

- **Main Path Analysis**(Hummon & Doreian 1989 / Batagelj 2003 の SPC)を使う。引用 DAG の全 source→sink パスを走ったときに何回通過されるかでエッジに重みを付ける、確立した手法。DAG なので前向き・後ろ向きの2パスで線形時間に計算できる。
- main path 1本だけでなく、**SPC 上位 p% のエッジからなる部分グラフ**(= 複数の並走するトラジェクトリ)を見せる。分野には流れが1本しかない、ということはない。

#### その太い線が何なのかを見分ける(重要)

ユーザーの直感通り、太いラインには少なくとも2種類ある:

- **(a) 特定ラボ / ラストオーサーの自己参照ライン** — 自分たちの研究を通すために引き続けている線
- **(b) 実際に分野として成立したトレンド** — 独立した複数グループが乗っている線

これは**計算で区別できる**。各バンドルについて、構成エッジの著者・所属の重複率を出す:

- 著者重複が高い → ラボ内部の系譜。**それ自体も見たい情報**なので消さず、別の色/記号で示す。
- 独立グループ数が多い → 分野トレンド。

**この判別を出せることが、既存ツールにない一番の差分になりうる。** 「太い線がある」だけなら main path analysis で既出だが、「その太さが誰によって作られたか」を可視化した例は見当たらない(要確認)。

### F3. 流れに名前を付ける(必須になった)

当初は「Related Work を LLM で全文解析」を構想していたが、**全文処理はやらない**(コスト・OA 制約・しんどさが見合わない)。代わりに:

1. **色分けは citation intent API のみで行う。** Semantic Scholar Graph API が返す intent(background / method / result)でエッジを色分けする。全文不要。
2. **LLM は「命名」にだけ使う。** F2 で取り出したバンドル / コミュニティごとに、代表論文のタイトル・会場・年レンジを渡して、短い名前と1行説明を生成させる。対象は論文10万本ではなく**バンドル数十〜数百個**なので、コストは無視できる。
3. 同様に、**画面全体のコンテキストに名前を付ける**(「この年代のこの帯は概ね〜」)のも安い。ズームレベルに応じたラベルの粒度切り替えとして使える。

LLM は解析エンジンではなく**ラベラー**、という位置づけを守る。

## Non-goals(明示的にやらないこと)

- **全文の LLM 解析をしない。**(2026-07-29 決定)Related Work セクション抽出も当面やらない。
- **文献管理ツールを作らない。** ライブラリ管理・PDF 保管は Paperpile / Zotero の役目。
- **推薦・discovery を主貢献にしない。** 「隠れた重要論文を見つける」は既存ツールの土俵。こちらは**分野の形を読む**ためのツール。
- **全分野の網羅を初手でやらない。** まず HCI(CHI / UIST / CSCW / DIS / TOCHI / IUI / UbiComp)で成立させる。
- **スクレイピングをしない。** OpenAlex snapshot / CLI と公開 API の範囲内。
- **精読のための UI を作り込まない。** 個別論文の詳細はズーム時の最小限で足りる。

## Success criteria

- HCI 主要会議の全論文(数万〜十万オーダー)を**一度に**描画でき、操作が破綻しない。
- その絵を見て、**知っている分野の流れが自分の記憶と一致する**(例: モバイル HCI → タンジブル → 制作系ファブリケーション、といった帯が見える)。ここが検証の要。一致しないならレイアウトが間違っている。
- 太いラインをクリックすると、それが「あるラボの系譜」なのか「複数グループのトレンド」なのかが判別できる。
- LLM が付けた流れの名前が、自分の言葉と大きくズレない。
- 描画結果が決定的(同じデータなら同じ絵)。

## オープンな問い

- **cross axis の決め方**。ここが成否を分ける → `algorithms.md` に候補を列挙。
- 時間軸は縦か横か。流れとして読ませるなら横(左→右)が有力だが、年レンジが長いと縦スクロールのほうが自然かもしれない。**プロトタイプで両方試す。**
- コーパスの範囲。HCI 会議のみで閉じると、外部(ML / システム / 認知科学)からの流入が切れる。会議で絞るか、topic で絞るか、seed から N ホップで到達可能な範囲を取るか。
- 「トレンド」の粒度。バンドル = トレンド、で人間の直感と合うのか。
